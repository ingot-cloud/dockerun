# Dockerun 一体化部署操作与接口

## 安装与持久化

首次安装、HTTPS、离线控制台镜像、升级及恢复命令见[部署指南](DEPLOYMENT.md)，完整环境变量见[配置参考](CONFIGURATION.md)。本文主要说明安装后的应用发布及接口行为。

统一镜像内含 Go 服务、网页、Distribution v3.1.2、Docker CLI、Compose 和数据库备份工具。运行时不启动额外 Registry 容器。入口为 `/`、`/api/`、`/v2/`、`/registry/token`（GET 与 BuildKit OAuth POST）。

设置 `PUBLIC_URL` 为客户端及 Docker daemon 可达的根地址；不能带路径、账号或查询参数。默认禁止匿名访问，初始化管理员前仓库不可用。直接 HTTPS 使用 `TLS_CERT`、`TLS_KEY`；已有反向代理需保留 Authorization、WWW-Authenticate、Location 等协议头，并允许大文件及流式响应。HTTP 本机验证与正式 HTTPS 配置应分别管理；Docker daemon 对 HTTP Registry 的要求沿用 Docker 标准配置。

Docker Desktop 本地开发时，宿主机 Go 服务与虚拟机中的 daemon 不在同一网络环境。本地 Make 命令默认设置 `PUBLIC_URL=http://host.docker.internal:8080`，执行 `make dev-backend` 即可使用该认证入口，无需额外传参。若 `docker login localhost:8080` 超时，但宿主机执行 `curl http://localhost:8080/v2/` 正常返回带 `WWW-Authenticate` 的 401，应从 daemon 环境检查宿主访问地址。使用 `host.docker.internal:8080` 登录时，认证令牌地址也必须使用此入口；已有后端进程需重启以应用配置。仅本地 HTTP 调试时，把该地址合并到 Docker Desktop 的 `insecure-registries` 并 Apply & Restart；已有配置应保留。Linux 本机 Docker Engine 可用 `make dev-backend PUBLIC_URL=http://localhost:8080` 覆盖，正式容器部署仍通过 `.env` 指定实际入口。步骤见[本地开发指南](DEVELOPMENT.md#本地-http-仓库调试)。

`DATA_DIR` 默认 `./data`，容器中为 `/var/lib/dockerun`：

| 目录 | 内容 |
|---|---|
| `keys/` | 网页、Registry、Distribution HTTP 状态及凭据加密密钥 |
| `registry/` | Distribution 管理的镜像内容与上传状态 |
| `dockerun.db` | 默认 SQLite 元数据；可切换专用 MySQL 数据库 |
| `uploads/` | 上传分块及已导入归档 |
| `releases/` | 离线解包材料 |
| `jobs/` | 渲染配置、任务材料与恢复定义 |
| `backups/` | 完整备份及升级前数据库快照 |
| `imports/` | 管理员可指定导入的服务器文件目录 |

目录需持久化，默认使用命名卷，也支持宿主目录绑定，容器内目录固定为 `/var/lib/dockerun`。两种模式均在发往本机 Docker 的请求中转换数据目录内的绑定源，兼容 Compose 相对路径、`configs.file` 和本地卷驱动的 bind 选项；业务容器的挂载目标不变。不要只备份数据库后将其当作完整镜像备份。`REGISTRY_ENABLED=false` 可以关闭内置引擎，不删除内容。原有外部 Registry 及默认选项保留。

## 用户与凭据

管理员可创建、启停、重设密码、调整角色及仓库权限。普通用户默认无仓库权限，仅能访问个人账号。只读可以浏览和拉取；读写增加推送。普通用户不能导入 Docker 镜像、导入发布包、部署应用、管理外部连接或宿主资源。最后一个启用管理员不能被停用或降级。

网页旧 AES 密码传输入口保留兼容，存储仍为 bcrypt。Docker 使用标准账号密码交换令牌，不使用网页加密格式。网页和 Registry JWT 的密钥、用途及 audience 独立；Registry 默认 300 秒，无刷新令牌。禁用、改密和授权更新递增认证版本，后续请求立即重新检查。已开始的数据流不强制中断。

新外部仓库凭据使用持久化密钥进行 AES-GCM 加密，兼容读取历史 AES-CBC 数据。若历史安装自定义过 `AES_KEY` / `AES_IV`，升级和恢复时保留相同配置，重新录入并保存凭据后会写入新格式。显式通过环境变量提供的签名或加密密钥也应纳入安装配置备份。

自动化令牌在个人页面创建，最长 90 天，默认 30 天，只显示一次。可选择 pull、push、deploy，不能超出当前账号授权；普通用户不能取得 deploy。自动化令牌不能管理账号、签发子令牌或管理宿主和系统。可通过 `docker login -u 用户名 --password-stdin` 将 Registry 令牌作为密码使用；页面命令不嵌入凭据。

外部 Registry 使用独立账号。Agent 默认不会接收管理连接凭据；管理员须另外配置在外部 Registry 中被限制为只读的拉取账号。外部账号的实际 ACL 由外部 Registry 执行；Dockerun 无法代替外部系统授予或撤销该 ACL。

## 在线发布

### 从应用模板开始

「发布工作区 → 应用模板」统一提供单服务应用、MySQL、Redis、Nacos 单机及 Nacos 单机三节点集群。选择模板，填写应用名称、首个环境、目标主机、镜像仓库和运行参数，点击「创建并准备发布」进入已填好的发布向导，检查后确认部署。创建与预览不会启动容器。

默认使用内置仓库，镜像必须先准备到所选仓库；也可以切换已有外部仓库，表单会保留镜像名称和版本、切换仓库地址。镜像版本沿用项目旧模板的固定版本，发布时继续锁定摘要，不自动跟随新标签。中间件默认手动更新；需要持续交付的业务应用，在保存部署配置后按环境配置镜像自动发布。

模板包含参数表单、Compose、非敏感配置文件、部署脚本、初始化说明和访问入口。应用记录创建来源及模板版本，并保存独立定义；修改或新增模板版本不会修改已有应用。首次网页发布成功准备版本后会保存尚未插值的应用定义，后续发布可沿用该定义，参数值仍属于对应环境。配置准备成功不等于服务已经部署成功。

MySQL、Redis 以及 Nacos 各节点采用环境独立的命名卷，卷名随应用及环境 ID 固定，重新部署和手动升级复用原数据。中间件不能通过无状态自动恢复回滚数据。应用详情展示持久化说明、首次初始化规则以及依据环境参数生成的连接地址；远程节点须替换为实际可达的主机地址。

Nacos 三节点模板在一台主机部署三个 Nacos 节点及独立 MySQL，MySQL 不映射宿主端口。集群建表文件来自 [Nacos 3.1.1 官方 SQL](https://github.com/alibaba/nacos/blob/3.1.1/distribution/conf/mysql-schema.sql)，保留原许可，并随程序打包；由 MySQL 在空卷首次启动时执行，不在每次发布时重复建表。更改初始密码不会修改已有数据库的实际密码。Nacos 健康检查验证服务端口，集群成员状态需在控制台确认。此模板不提供跨主机高可用，页面及接口拒绝用固定主机组重复部署来代替集群编排。

「另存为应用模板」保存当前应用的未插值定义、非敏感文件和应用脚本，以新名称与版本存储，不覆盖已有模板。环境参数值、主机及业务数据不会复制；Compose 中可识别的固定凭据和绝对数据路径转换成待填写参数，固定容器名移除，普通数据卷重新按环境隔离。脚本及非敏感配置文件中的固定凭据需由管理员确认并移入环境参数。自定义模板随后出现在同一列表中。

「系统管理 → 历史脚本」继续兼容原有独立脚本与其旧模板，只支持手动执行；新服务从应用模板创建。本轮迁移上述常用中间件，其他旧脚本不会被自动执行、改写或重建已有容器。跨主机集群编排及自动数据库迁移需另行实现。

1. 创建应用，添加 test / prod 等环境，选择本机、Agent 或固定主机组。
2. 保存环境参数及健康、无状态和恢复策略。生产默认手动发布。
3. 命令部署由命令处理镜像。Compose 默认按镜像地址拉取，也可选择内置或外部仓库，提供包含所选仓库域名的引用；仓库模式在版本创建时解析并保存 digest。
4. 使用自定义命令、`docker run` 或 Compose 描述部署。受管理的 Compose 流程在开发机完成构建，部署阶段禁止 build；配置放入 `configs/`，敏感值使用环境运行参数。
5. 预览定义、镜像、目标及当前 Compose，确认后创建任务。
6. Compose 执行器准备全部镜像、生成锁定镜像的配置，执行部署前脚本，检查平台/端口/挂载/网络，再启动本应用 project，核对实际 Image ID 和健康，最后执行部署后脚本。命令部署流程见下节。

### 命令与 Compose 发布工作区

「发布应用」采用部署内容、运行参数、前后置脚本、高级配置四个标签页，顶部固定环境和操作，工作区填满剩余宽度和高度，长代码在编辑器内部滚动，参数及高级表单在当前面板内滚动。部署文件使用全宽大编辑器，按文件扩展名高亮，支持手动选择语法、查找及放大编辑；切换标签页、环境和文件保留草稿，切换文件保留光标、滚动和撤销记录。配置文件仍限定在 `configs/` 下，内容按原文保存。应用及环境脚本、历史脚本主文件与附加文件共用代码编辑器；脚本编辑弹窗的标题和保存操作固定，中部编辑区域填满可用空间，不撑出视口。

命令部署支持直接粘贴 `docker run` 或多行 Bash 命令，通过 `"$变量名"` 使用环境参数。默认由命令处理镜像拉取、登录及已有容器替换；也可在环境中关联容器并开启「部署时由系统替换关联容器」，由系统负责停止和删除明确关联的容器，数据卷保留。Compose 部署可直接按镜像地址在执行节点拉取，也可选择已配置仓库并锁定摘要、已有镜像或完整发布包。按地址拉取模式在执行时确定镜像身份，需要发布前锁定身份时使用已配置仓库来源。

发布页「镜像来源」旁的提示图标说明四种 Compose 来源；选择已配置仓库后，在同一区域选择实际仓库并核对地址。

| 镜像来源 | 获取方式与认证 | 适用场景 |
| --- | --- | --- |
| 按镜像地址拉取 | 按 Compose 的镜像地址拉取，不使用已配置仓库的认证，不自动将标签锁定为摘要。 | 公开、允许匿名拉取的镜像。 |
| 已配置仓库（锁定镜像摘要） | 使用所选仓库的认证；创建版本时固定摘要，后续部署使用同一镜像。内置仓库使用系统令牌，本机部署外部仓库使用已保存的身份认证，远程 Agent 使用独立的只读拉取账号。 | 私有仓库及需要固定镜像身份的发布。 |
| 目标主机已有镜像 | 不在线拉取，核对固定 Image ID。创建版本时先在 Dockerun 本机核对镜像，远程目标也须提前准备同一镜像。 | 已提前构建、拉取或导入的镜像。 |
| 完整发布包 | 从包含部署定义、配置文件和镜像归档等材料的完整包加载，不在线拉取。与单独的 `docker save` 归档不同。 | 离线部署、内网交付及迁移。 |

Compose 先准备镜像，再执行前置脚本，所以前置脚本中的 `docker login` 不能补充镜像准备阶段的认证。调整来源后应重新预览并创建新版本；重新部署旧版本仍使用其保存的来源。

在「高级配置 → 容器名称与网络」中按 Compose 服务分别设置容器名称与连接网络，部署内容页也提供直达入口。容器名称留空使用 Compose 自动名称，填写固定名称时须在同一主机上唯一；也可填写 `${变量名}` 并在运行参数中提供不同环境的名称，多副本服务应保留自动名称。命令部署的名称通过 `docker run --name` 设置。

连接网络留空使用应用默认网络；本机目标可选择网络管理中已有的自定义网络并刷新列表，支持多选。所选已有网络以外部网络写入 Compose，部署不会创建或删除该网络；保留原有连接的别名和固定地址。远程目标及固定主机组通过输入网络名称配置，每台目标主机须提前存在同名网络，不展示本机网络作为远程可用列表。系统网络通过 Compose 的 `network_mode` 配置，入口网络及不允许独立容器连接的 Swarm 网络不可选。使用 YAML 锚点或合并的服务请直接编辑部署内容，避免影响共享配置。

上述表单与 Compose 编辑器使用同一份部署草稿。保存配置供新版本使用，不立即重命名运行容器或更改网络；预览可核对生成的配置，确认发布后才生效，历史版本及已提交任务不变。

Compose 发布预览默认按服务展示概览，列出容器名称、镜像、锁定摘要、端口、网络、数据挂载、配置文件、重启策略及健康检查；「Compose 详情」展示格式化的只读 YAML。敏感运行参数继续脱敏，概览不展开变量值及内部临时路径。当前版本的镜像清单单独展示，保存的变量引用不按本次环境参数重新解析；此视图表示版本配置，实际运行镜像仍以容器核对结果为准。命令部署继续显示 Shell 命令，历史版本部署也可查看同样的服务概览与 YAML 详情。

受管 Compose 仍按固定 Image ID 启动并核对，容器上同时记录与该 ID 绑定的镜像名称。容器列表和详情优先显示经过身份核对的名称，Image ID 单独保留，镜像详情链接按实际 ID 跳转。旧容器可从本机已核对的运行记录补充名称；非受管容器可使用 Docker 为同一 ID 返回的唯一标签。无法确认身份、只有远程记录、存在多个候选标签或镜像查询失败时，保留原始镜像字段，不推测名称；展示名称不会重新拉取镜像、改写标签或重建容器。

应用详情提供「编辑部署配置」，可直接维护部署命令、Compose、配置文件和前后置脚本。「保存配置」只保存定义和所选环境的参数、有效脚本，不创建版本或任务；后续手动和自动创建的新版本使用保存后的配置。应用定义由各环境共用，运行参数和独立附加脚本属于环境。历史版本和已提交任务不会被改写。「发布版本」提供「基于此版本编辑」，复制快照为独立草稿，保存后更新应用配置；「部署此版本」可以部署到其他环境，也可以重新部署历史版本。该入口使用独立的只读视图，仅可选择目标环境；运行参数取环境当前已保存值，附加脚本按环境规则生效，部署命令、配置文件及已配置的执行信息按需展开查看，不提供保存配置、参数编辑或版本切换。确认部署前仍执行预检查，页面不保存应用或环境配置。「预览发布」先校验所有标签页并保存配置，然后准备版本，检查定义或命令语法，不执行脚本；「确认发布」才创建执行快照。参数或脚本在预览后变化时，确认请求会拒绝，须重新预览。脚本沿用应用默认、环境覆盖和停用规则，停用脚本不会停用主部署命令。

命令部署按前置脚本、部署命令、可选检查命令、后置脚本顺序执行，非零退出码停止后续阶段。未关联容器且未配置检查时只记录命令执行完成，服务运行状态保持未知；关联容器后核对实际运行状态和 Image ID，不将命令退出成功直接当作容器更新成功。脚本日志按敏感参数名称及模板密码类型脱敏，跨输出分段的值也会隐藏。后置失败明确记录部署命令已经执行。命令部署不自动回滚，不在进程中断后自动重跑；管理员可核对结果后重新发布。Compose 保留镜像、服务及健康核对，支持额外检查命令。

高级配置支持脚本工作目录、任务超时和检查命令。默认工作目录为任务目录，`WORK_DIR` 始终指向该任务目录；自定义目录须在执行节点存在，配置文件仍写入任务目录。超时为 0 时使用系统设置，否则 1 至 86400 秒，各阶段共享超时。远程执行需更新 Agent；旧 Agent 会明确拒绝不支持的执行配置。

### 应用和环境的部署脚本

在应用详情的「应用附加脚本」中配置部署前、部署后 Bash 脚本；已有旧 Compose 启动脚本继续兼容，主启动命令统一在部署配置中编辑。应用脚本在创建新版本时保存快照，之后编辑不会改变已有版本；手动发布、镜像自动发布、从完整包创建的新版本都采用此规则。

环境高级配置的「附加脚本来源」可选择「使用版本中的应用附加脚本」「使用此环境的独立附加脚本」「不执行附加脚本」。此规则控制前后置及兼容的旧启动脚本，不停用主部署命令或部署检查；仅普通 Compose 未填写主命令时由系统启动。环境独立脚本在提交任务时保存快照，固定主机组中的每台主机使用同一配置。脚本在实际目标执行器中运行：本机任务在 Dockerun 运行环境中执行，远程任务在对应 Agent 主机上执行；需要的 Bash、命令和目录必须在该执行环境可用。控制台及 Agent 均需更新到支持脚本的版本。

发布脚本与系统 Compose 命令保留服务进程的 `PATH` 优先级，并补充系统命令目录、`$HOME/.docker/bin`；macOS 另补充 Homebrew 与 Docker Desktop 的 CLI 目录，避免从桌面程序或服务启动时找不到已安装的 `docker`。执行器不会加载交互式 Shell 配置。环境参数显式设置 `PATH` 时，脚本使用该值；Docker CLI 仍须安装在实际执行环境内。出现 `docker: command not found` 时，检查执行器所在主机或容器中的 CLI 安装与路径，而非镜像地址。

部署脚本留空时系统运行 Compose；填写后由脚本接管启动步骤，系统仍要求应用栈中的服务运行且镜像身份一致。部署前脚本可创建挂载目录或准备外部资源，部署后脚本可追加检查；任一脚本退出码非零会使任务失败，失败命令或管道不会继续执行后续脚本。预检查页面只展示脚本，不执行。

脚本工作目录为当前任务目录，`configs/` 中包含该版本的非敏感配置。环境参数作为环境变量传入，另提供 `WORK_DIR`、`HOST_WORK_DIR`、`COMPOSE_FILE`、`COMPOSE_PROJECT_NAME`、`DOCKERUN_APPLICATION_ID`、`DOCKERUN_ENVIRONMENT_ID`、`DOCKERUN_ENVIRONMENT`、`DOCKERUN_VERSION`。系统变量以实际任务为准。自定义部署脚本的最小示例：

```bash
docker compose --env-file "$WORK_DIR/empty.env" \
  --project-name "$COMPOSE_PROJECT_NAME" --project-directory "$WORK_DIR" \
  -f "$COMPOSE_FILE" up -d --pull never --no-build --wait --wait-timeout 120
```

`WORK_DIR` 用于在执行环境中读取配置、切换目录；`HOST_WORK_DIR` 是同一目录在目标 Docker 主机上的路径，供明确需要宿主路径的工具使用。默认 Docker 连接已由执行器设置，脚本中的 `docker run -v "$WORK_DIR/configs/app.conf:/app.conf:ro"`、`--mount type=bind` 和 Compose 会自动转换绑定源，无需手动拼卷挂载点。脚本正文、环境变量值和业务容器内路径不会被全局替换；显式指定其他 `--host`、`--context`、自行覆盖 Docker 连接或调用其他容器运行时的脚本需自行对齐路径。

兼容旧目录绑定配置中保存的数据根路径，受管 Compose 的绑定源、配置文件和脚本工作目录会归一到容器内路径。旧 Shell 若直接用宿主绝对路径读取文件，应改用 `WORK_DIR` 或 `/var/lib/dockerun` 下的容器路径；数据根之外的宿主绑定源按原样交给 Docker。远程 Agent 按自身数据目录执行，不使用控制台命名卷的挂载点。

所有阶段共享任务超时，日志按阶段持久化。脚本执行被进程重启打断时标记为「需要核对」，不会自动重跑。持久数据应放在环境指定的挂载路径；任务目录属于单次发布。自动恢复只恢复上一成功版本的服务和配置，不重跑其脚本，也不撤销脚本修改的数据库或外部系统。恢复历史成功配置时同时恢复当时的环境参数和有效脚本。历史脚本入口继续保留；已有脚本可人工迁移到应用或环境配置，附加配置文件放入发布版本的 `configs/`。

任务与浏览器连接无关。历史与 SSE 可重新读取。进程重启后排队任务继续；已开始任务先对账，无法确认时标为“需要核对”，不盲目重复替换。应用的部署结果、运行状态和健康分别存储；没有健康检查时显示“已启动，未验证健康”。

自动恢复仅限明确无状态且开启策略的环境。恢复使用上次成功的配置和镜像身份，生成的失败记录保留，恢复结果单独展示。应用数据卷不由该功能回滚或清空。默认保护各环境、目标最近 3 个成功版本、当前版本以及排队/执行中版本。

## 自动发布授权

在应用保存有效部署配置后，通过「部署环境」行的「自动发布」，或「应用配置」中的环境入口，直接配置监听仓库、镜像名称（例如 `team/gateway`，不含域名和标签）、标签规则（如 `latest`、`test-*`、`*`）及允许触发的用户。此入口可保存触发规则、关联容器及替换策略，不改写运行参数、主机、附加脚本或恢复策略，也不创建任务。已有安装尚未保存应用定义时，继续以该环境当前成功的仓库版本作为基础。

Compose 自动发布使用最新保存的 Compose、配置文件、启动和检查命令，以及当前环境参数和有效附加脚本；新版本固定触发镜像的 digest，其他镜像在版本创建时解析摘要。监听镜像必须包含在保存后的配置中，镜像地址须属于监听仓库；本机和完整发布包来源需先保存为在线部署配置。保存配置不会访问远端仓库或执行脚本。

命令部署也支持自动发布，不要求先生成 Compose 或完成首次手动发布。先在保存后的主部署命令中引用 `$DOCKERUN_IMAGE`，再为环境绑定监听规则。触发后，系统通过 Docker API 与已配置的仓库凭据在目标节点准备固定摘要的镜像，再执行命令；未开启系统替换时，容器替换逻辑由脚本负责。系统提供 `DOCKERUN_IMAGE`（含 digest 的完整镜像引用）、`DOCKERUN_IMAGE_TAG`（触发标签）、`DOCKERUN_IMAGE_DIGEST`（摘要），环境参数不能覆盖这些触发值。兼容手动部署的引用示例：

```bash
docker run -d --name "$APP_NAME" --restart unless-stopped \
  "${DOCKERUN_IMAGE:-$IMAGE}"
```

其中 `IMAGE` 为手动部署的环境参数。未开启系统替换时，重复部署由脚本处理已有容器；开启后脚本只需创建新容器。通过「部署此版本」部署自动生成的命令版本时仍使用该版本的固定镜像。远程 Agent 需支持 `command_images=1`，关联容器的任务还需支持 `containers=1`；旧 Agent 会明确拒绝此类任务。

环境编辑、发布工作区的高级配置及自动发布配置提供「关联容器」，例如 `test-nginx`，或引用运行参数 `$APP_NAME`。同一主机的同名容器不能关联多个环境；尚未结束的其他环境任务也保留对原容器的关联。系统不会从任意 Shell 脚本猜测容器归属。命令环境开启「部署时由系统替换关联容器」后，先校验配置、工作目录及全部关联容器的归属，再按任务类型执行：

- 手动发布和「部署此版本」：先加载或准备版本锁定的镜像，镜像校验失败时保留旧服务；就绪后停止并删除目标环境已关联的旧容器，保留数据卷，再运行此版本脚本。容器不存在时直接运行。手动发布不清理镜像；离线来源仅加载镜像，不拉取仓库。仓库历史版本继续使用其锁定摘要。
- 自动命令发布：停止并删除关联容器后，检查本次触发镜像的 tag 是否已经存在；只有存在时才清理该 tag 的可删除引用，不存在时跳过。仍被其他容器使用的镜像保留，不强制删除共享镜像。随后按固定 digest 拉取、将本地 tag 指向本次 Image ID，再执行脚本。
- 系统管理的 Compose 手动发布：准备全部镜像后重建当前应用环境的服务，并移除该项目中已不属于版本定义的旧服务；相同版本重部署也会重建容器。自动 Compose 发布继续只更新变化的服务。

手动部署自动生成的历史版本仍按手动规则执行，不因版本携带触发镜像而清理本地镜像。没有镜像元数据的命令版本由脚本准备镜像。各阶段持久化日志，失败后核对关联容器实际状态；已删除的旧容器不会自动恢复。预览展示关联范围与替换策略，确认前配置变化时拒绝提交，历史版本及已提交任务保持原快照。远程手动任务与关联容器任务要求 Agent 声明 `release_policy=2`，需同时更新控制台和 Agent。

自动发布按「仓库、镜像名称、tag、digest」与各目标最新排队目标比较；没有排队任务时与当前成功版本比较：同 tag 且同 digest 跳过，不重启；不同 tag 即使 digest 相同也创建替换任务；同 tag 但 digest 变化正常更新。Compose 为触发服务保存镜像标签标记，使相同内容的不同 tag 也能触发更新；未变化的其他服务保持原配置。重复推送事件独立接收，与最新排队目标相同的镜像不重复提交，切回曾经使用过的 tag 仍可部署。

应用的「部署环境」显示正在运行的镜像名称与短 Image ID；「应用配置 → 运行容器与镜像」显示各环境、主机、容器、完整镜像引用、完整 Image ID、状态及核对时间。信息来自 Docker 实际检查，不以目标版本推测。命令部署需关联容器，Compose 自动按本应用项目记录；本机定期核对，远程主机在部署结束后上报，页面明确显示最近核对时间。

内置仓库为新配置的默认来源，完整 manifest / 最终命名索引提交后记入持久化事件，**无需配置 Webhook、回调地址或密钥**。匹配推送使用已保存的部署配置生成新版本，再按推送人授权决定是否自动提交任务；新版本、任务均保存固定快照。Buildx 子 manifest、包导入及显式包镜像入库不触发自动替换。

管理员推送默认可触发已启用的环境；普通用户须在该环境的允许推送人列表中。创建及执行任务都检查当前资格。普通推送也可形成待发布版本。包导入和显式包镜像入库不触发自动替换。

外部 Webhook 要求启用、配置密钥，并由管理员保存来源规则。请求必须验签，镜像 digest 须从已配置 Registry 实际确认，才能持久化处理。载荷 actor 不作为 Dockerun 用户。旧来源和目标没有明确绑定的自动脚本在升级时关闭，保留定义供人工迁移。

## 离线发布包

```text
application-release.tar.gz
├── release.json
├── compose.yaml
├── images/*.tar
├── configs/*
├── env.example
└── checksums.sha256
```

`release.json` 的 `schema_version=1`，记录应用、版本、目标平台、每个镜像完整 Image ID、归档路径及 SHA-256。一个包包含一个应用栈所有服务镜像，支持 Linux amd64 或 arm64。外部依赖明确说明；生产密码、数据卷和可执行安装脚本不放入包中。

```bash
# 已在开发机准备好所选平台镜像；默认不联网补齐。
dockerun package gateway --file compose.yaml --platform linux/amd64 --output gateway-release.tar.gz
# --defaults defaults.json 仅提供非敏感打包插值默认值。
dockerun import gateway-release.tar.gz --wait
dockerun deploy gateway --env prod --bundle gateway-release.tar.gz --wait
```

在应用中先创建部署环境，再点击「发布应用」。命令部署的「镜像来源」可选择「离线镜像归档」或「完整发布包中的镜像」，直接在发布页上传新包或选择已导入材料，不必离开脚本编辑器。首次编辑部署脚本、关联容器并保存配置，后续发布选择相同环境、导入新包即可复用脚本和参数。多镜像包须明确选择脚本主镜像；`DOCKERUN_IMAGE` 为此版本的固定 Image ID，环境参数不能覆盖它。使用包内 Compose 时选择「完整发布包」。

离线命令版本保留归档、镜像清单、Image ID 和脚本快照。每次实际执行（包括历史版本重部署）在目标节点重新加载保留的归档并核对镜像身份，再替换容器；导入本身不停止服务，也不触发自动发布。自定义脚本如需其他网络操作，由脚本内容决定。

网页支持完整包和普通 `docker save` 归档两种材料，分块最大 16 MiB，客户端使用 8 MiB。文件 SHA-256 标识上传，偏移校验与 fsync 支持续传。服务器目录导入只读取 `IMPORT_DIR` 内文件。未知格式、错误平台、缺少镜像、校验失败、重复路径、越界路径、链接和特殊文件都会拒绝。

控制台和包平台一致时，校验通过后加载本机；平台不一致时仅保存完整材料，明确显示“由目标节点确认”，不将控制台状态视为其他节点已就绪。节点加载时解析 Docker 的 JSON 错误帧，再检查实际加载的 Image ID 和平台。导入只准备材料；创建待发布版本时不修改已有环境参数。严格离线运行只引用已有 Image ID，禁用拉取、构建、远程 include、extends、env_file 与不明确的 profiles。

仓库、Docker 本机缓存和离线材料是三类独立存储。本机导入不会自动入库；管理员可通过 `/api/bundles/publish` 显式将已导入包版本镜像推送到内置仓库，生成在线版本用于内网复用。

## CLI 与 Agent

开发构建使用现有 Docker Compose / Buildx；可用 `--build-script ./build.sh` 复用脚本。缓存默认开启，`--no-cache` 显式关闭；默认从目标元数据取得平台，也可显式 `--platform`。跨架构组需要具备多平台能力的 builder。

```bash
dockerun deploy gateway --env test --build --wait
dockerun deploy gateway --env test --release 12 --wait
dockerun promote gateway --release 12 --to prod --wait
dockerun rollback gateway --release 10 --env prod --wait
dockerun status 42
```

失败返回非零退出码，`--wait` 返回实际任务结果，主机组会等全部节点。版本晋升保持镜像身份并采用目标环境参数。恢复可选择该版本在此环境上次成功的配置；CLI rollback 默认请求恢复该配置，找不到历史快照时明确拒绝。网页确认差异后再发布；历史配置快照用于失败自动恢复。

Agent 要求 HTTPS，回环地址仅供本机验证。通过 `DOCKERUN_URL`、`DOCKERUN_AGENT_TOKEN` 和持久化 `--data-dir` 启动。实例标识、文件锁、任务租约、本机执行日志和结果文件共同避免重复替换。凭据只访问绑定节点任务，不能管理用户或其他节点。目标离线保持等待，不自动改派。固定组逐机准备、部署、检查；失败暂停后续目标，逐节点记录真实版本。

## 维护与恢复

仓库维护先切换只读，等待在途请求结束，再创建持久化 GC 任务，保留未打标签的 manifest。任务在后台执行，离开页面不会中断；完成后保持管理员开启的只读状态。原始 `/v2/` 和网页删除都检查保护引用；镜像层不开放独立 DELETE，交由 GC 清理。

管理员从“仓库与维护”创建持久化完整备份任务，刷新页面后仍可查询状态并下载结果。SQLite 使用一致性快照；MySQL 通过 `mysqldump --single-transaction`。本机执行和包导入在备份窗口暂停，Registry 只读。备份包含元数据、keys、Registry 内容、发布材料和任务材料；业务数据卷及外部 Registry 自身内容需单独备份。

备份和 GC 任务按提交顺序串行执行，同类任务排队或执行期间重复提交会返回已有任务。备份结束后恢复原来的手动维护状态，执行中不能恢复写入；排队或运行中的 GC 也会阻止结束只读维护。页面只在存在活动任务时轮询；失败任务可重新提交。进程重启后，正在运行的任务会标记为失败，未完成的备份不会提供下载。

```bash
# 停止当前 Dockerun，恢复到新的空目录；不会覆盖已有目录。
dockerun restore --file dockerun-backup.tar.gz --data-dir /var/lib/dockerun-restored
```

MySQL 备份会解出 `metadata.sql`，需恢复到专用 MySQL 数据库，再配置连接启动。不要将材料已解包视为数据库已恢复。使用原安装的外部密钥配置；导入材料路径会在启动时依据恢复目录重新定位。仅数据库文件不属于完整备份。

## API 摘要

| API | 行为 |
|---|---|
| `GET/POST /api/users`、`PATCH /api/users/:id` | 管理员账号维护 |
| `GET /api/auth/me`、`POST /api/auth/change-password` | 本人信息与密码 |
| `GET/POST/DELETE /api/auth/tokens[/:id]` | 本人自动化令牌 |
| `GET /api/builtin/catalog`、`GET /api/builtin/tags` | 有权限用户浏览内置仓库 |
| `DELETE /api/builtin/manifests` | 管理员受保护删除 |
| `POST /api/builtin/maintenance` | 指定 `read_only` 切换管理员只读窗口；只读窗口内以 `gc: true` 创建后台 GC 任务，返回 `job_id` |
| `GET /api/builtin/maintenance` | 最近 100 条 GC 任务及执行结果 |
| `GET/POST /api/system/backups`、`GET /api/system/backups/:id/download` | 完整备份任务及已完成文件下载 |
| `GET/POST /api/applications`、`GET /api/applications/:id` | 应用及环境、版本 |
| `GET /api/managed-templates` | 内置及自定义应用模板，含版本、参数表单及独立应用定义 |
| `POST /api/managed-templates/:id/applications` | 原子创建应用及首个环境；校验目标主机和模板参数，不直接部署 |
| `POST /api/applications/:id/template` | 将未插值的应用定义保存为新的自定义模板版本 |
| `PUT /api/applications/:id/deployment-config` | 保存部署定义、非敏感文件、执行配置和当前环境有效脚本；不创建任务 |
| `PUT /api/applications/:id/scripts` | 管理员保存应用脚本，正文为 `{"scripts":{"before":"…","deploy":"…","after":"…"}}` |
| `PUT /api/applications/:id/environments` | 创建或更新环境，支持固定目标列表；`script_mode` 为 `inherit`、`override` 或 `disabled`，`scripts` 为独立脚本；未指定仓库时采用内置来源 |
| `PATCH /api/applications/:id/environments/:environment_id/parameters` | 仅更新运行参数，保留主机、脚本及发布策略；`expected_parameters` 可检查编辑期间的参数冲突 |
| `PATCH /api/applications/:id/environments/:environment_id/automation` | 独立保存环境自动发布规则，可选保存 `container_names`、`replace_containers` |
| `POST /api/applications/:id/releases` | 创建不可变本机/仓库/离线命令版本 |
| `POST /api/deployments/preflight` | 定义与差异预览，执行前再检查镜像及资源；可用 `expected_parameters`、`expected_containers` 校验本次确认的环境参数及容器策略 |
| `POST /api/deployments` | 以幂等标识创建持久化任务；`restore_configuration` 可请求历史成功参数，`expected_parameters`、`expected_containers` 可阻止已确认参数或容器策略变化后继续部署 |
| `GET /api/deployments[/:id]`、`GET /api/deployments/:id/events` | 历史、逐机状态、增量日志及 SSE |
| `POST /api/releases/:id/promote` | 用相同镜像身份在目标环境创建新任务 |
| `GET/PUT /api/bundles/uploads/:sha256` | 上传偏移与分块 |
| `POST /api/bundles/uploads/:sha256/complete` | 校验并创建异步导入任务 |
| `POST /api/bundles/:id/version` | 确认材料为待发布版本 |
| `POST /api/bundles/publish` | 显式将包版本镜像入库 |
| `GET/POST/PATCH /api/targets[/:id]` | 管理员主机配置 |
| `/agent/poll`、`/agent/tasks/:id/...` | 绑定节点领取、心跳、日志及结果 |

所有业务管理接口均在服务端鉴权，普通用户无法通过直接请求绕过菜单。历史 Shell 通过统一任务、日志和超时保留兼容；离线命令支持受管镜像加载与容器替换，通用恢复仍用于受管 Compose。

### Compose 项目名称

在发布页「高级配置」或应用的「环境配置」中，可在首次部署前填写「Compose 项目名称」。留空沿用 `dockerun-a<应用编号>-e<环境编号>`，例如 `dockerun-a7-e5`；已有环境留空时继续使用原名称。

- 名称按环境保存，同一应用的不同环境可分别设置。名称须以小写字母或数字开头，仅含小写字母、数字、连字符和下划线，最多 100 个字符；`dockerun-a编号-e编号` 为系统保留格式。
- 同一目标主机上的不同环境不能使用同名项目；多主机环境按全部目标校验。不同主机可以使用同名项目。
- 此配置优先于 Compose 顶层 `name:` 及运行参数里的 `COMPOSE_PROJECT_NAME`。系统会向脚本提供实际的 `COMPOSE_PROJECT_NAME`，不需要通过运行参数设置。
- 项目名称用于 Compose 资源分组及默认网络、项目数据卷和自动生成的容器名称前缀。它不是镜像名称，也不是服务在网络中的访问地址；服务间仍通过共享网络上的服务名、容器名或网络别名访问。
- 一旦提交过部署任务，项目名称即固定，包括排队、失败、取消及已隐藏历史的任务。本次不支持对已部署环境改名或迁移数据卷；预览及历史版本部署均采用目标环境的已保存名称。
- 发布预览显示实际名称；预览后若配置变化，须重新预览。自定义名称也保存在执行快照中；远程目标需更新 Agent，以支持该字段，旧 Agent 会明确拒绝任务。
